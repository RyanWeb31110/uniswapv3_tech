## 一、获取用户流动性仓位

### 1.1 为什么需要获取仓位信息？

在实现移除流动性功能之前，我们需要让用户知道：
- 他们在哪些价格区间有流动性仓位？
- 每个仓位有多少流动性？
- 累计了多少手续费？

这些信息存储在资金池合约中，我们需要通过智能合约接口来获取。

### 1.2 添加 Manager 辅助函数

为了简化前端操作，我们在 Manager 合约中添加一个辅助函数，用于获取用户在特定资金池中的仓位信息：

```solidity
/// @notice 获取用户在指定资金池中的流动性仓位信息
/// @param params 仓位查询参数（包含代币地址、费率、仓位所有者、价格区间）
/// @return liquidity 流动性数量
/// @return feeGrowthInside0LastX128 token0 的内部手续费增长（上次更新时的值）
/// @return feeGrowthInside1LastX128 token1 的内部手续费增长（上次更新时的值）
/// @return tokensOwed0 待领取的 token0 手续费
/// @return tokensOwed1 待领取的 token1 手续费
function getPosition(GetPositionParams calldata params)
    public
    view
    returns (
        uint128 liquidity,
        uint256 feeGrowthInside0LastX128,
        uint256 feeGrowthInside1LastX128,
        uint128 tokensOwed0,
        uint128 tokensOwed1
    )
{
    // 通过代币对和费率获取资金池合约
    IUniswapV3Pool pool = getPool(params.tokenA, params.tokenB, params.fee);

    // 从资金池合约读取仓位信息
    // 仓位键 = keccak256(owner, lowerTick, upperTick)
    (
        liquidity,
        feeGrowthInside0LastX128,
        feeGrowthInside1LastX128,
        tokensOwed0,
        tokensOwed1
    ) = pool.positions(
        keccak256(
            abi.encodePacked(
                params.owner,      // 仓位所有者地址
                params.lowerTick,  // 价格区间下界
                params.upperTick   // 价格区间上界
            )
        )
    );
}
```

**这个辅助函数的好处**：
- ✅ 封装了资金池地址计算逻辑
- ✅ 封装了仓位键（position key）的计算逻辑
- ✅ 前端只需传入代币地址、费率和价格区间即可
- ✅ 避免在前端进行复杂的哈希计算

### 1.3 理解返回值：两种手续费的区别

`getPosition` 函数返回了两组与手续费相关的值，它们有着不同的含义和用途：

#### feeGrowthInsideLastX128 - 手续费增长快照

```solidity
uint256 feeGrowthInside0LastX128;  // token0 的手续费增长快照
uint256 feeGrowthInside1LastX128;  // token1 的手续费增长快照
```

**作用**：

- 📸 记录**上次更新仓位时**的手续费增长快照值
- 🧮 用于**计算新增手续费**的基准值
- 🔄 每次 `mint`、`burn` 或 `collect` 时会更新

**计算公式**：
```
新增手续费 = (当前全局增长 - 上次快照增长) × 流动性 / 2^128
```

#### tokensOwed - 待领取的手续费

```solidity
uint128 tokensOwed0;  // 可领取的 token0 手续费数量
uint128 tokensOwed1;  // 可领取的 token1 手续费数量
```

**作用**：
- 💰 存储已经**计算好**的、可以直接领取的手续费数量
- ✅ 调用 `collect` 函数时会转账这些代币
- 📦 包含了所有**已结算但未领取**的手续费

#### 两者的关系示例

假设你在 USDC/ETH 池子中提供流动性，时间线如下：

```javascript
// === T0: 初始添加流动性 ===
mint(liquidity: 1000)

仓位状态：
  feeGrowthInside0LastX128 = 100  // 当前全局增长快照
  feeGrowthInside1LastX128 = 200
  tokensOwed0 = 0                 // 刚添加，没有待领取手续费
  tokensOwed1 = 0

// === T1: 交易发生，手续费累积（全局状态变化）===
全局状态：
  feeGrowthInside0 = 150  // 增长了 50
  feeGrowthInside1 = 250  // 增长了 50

你的仓位（还未更新）：
  feeGrowthInside0LastX128 = 100  // 仍是旧值
  tokensOwed0 = 0                 // 还未结算

// === T2: 你移除了部分流动性 ===
burn(liquidity: 400)

// 触发手续费结算：
新增手续费0 = (150 - 100) × 1000 / 2^128 = X
新增手续费1 = (250 - 200) × 1000 / 2^128 = Y

更新后的仓位：
  feeGrowthInside0LastX128 = 150  // 更新为当前值（新快照）
  feeGrowthInside1LastX128 = 250
  tokensOwed0 = X                 // 结算的手续费可以领取了
  tokensOwed1 = Y
  liquidity = 600                 // 剩余流动性

// === T3: 领取手续费 ===
collect()

全局状态（又增长了）：
  feeGrowthInside0 = 180  // 又增长了 30

计算新增手续费：
  新增手续费0 = (180 - 150) × 600 / 2^128

最终领取：
  实际领取0 = X + 新增手续费0  // 之前累积的 + 新增的
  实际领取1 = Y + 新增手续费1

领取后：
  tokensOwed0 = 0                 // 清零
  tokensOwed1 = 0
  feeGrowthInside0LastX128 = 180  // 更新快照
  feeGrowthInside1LastX128 = 280
```

#### 核心区别总结

| 特性 | feeGrowthInsideLastX128 | tokensOwed |
|-----|------------------------|-----------|
| **类型** | 累计增长快照（Q128.128） | 实际代币数量（wei） |
| **用途** | 用于**计算**手续费 | 存储**待领取**的手续费 |
| **更新时机** | 每次修改仓位时更新为当前全局值 | 每次结算时累加新增手续费 |
| **初始值** | 当前全局 feeGrowthInside | 0 |
| **领取后** | 保持当前快照值 | 归零 |
| **前端使用** | 通常不直接显示给用户 | 直接显示为"可领取手续费" |

**为什么需要这种两阶段设计？**

1. **Gas 优化** ⛽：不需要每次查询都重新计算手续费，只在必要时（修改仓位）才结算
2. **精度保证** 🎯：使用 Q128.128 高精度格式存储增长率，避免小额手续费的精度损失
3. **灵活性** 🔄：手续费可以累积，不必每次都领取，支持批量领取

### 1.4 前端调用示例

在用户输入价格区间后，我们可以立即查询该区间是否有流动性仓位：

```javascript
/**
 * 获取用户可用的流动性数量
 * 使用 debounce 避免频繁调用合约（用户输入时）
 */
const getAvailableLiquidity = debounce((amount, isLower) => {
  // 将价格转换为 Tick 值
  const lowerTick = priceToTick(isLower ? amount : lowerPrice);
  const upperTick = priceToTick(isLower ? upperPrice : amount);

  // 构建查询参数
  const params = {
    tokenA: token0.address,
    tokenB: token1.address,
    fee: fee,                    // 费率档位（500/3000/10000）
    owner: account,              // 当前用户地址
    lowerTick: nearestUsableTick(lowerTick, feeToSpacing[fee]),  // 对齐到有效 Tick
    upperTick: nearestUsableTick(upperTick, feeToSpacing[fee]),  // 对齐到有效 Tick
  }

  // 调用 Manager 合约的 getPosition 函数
  manager.getPosition(params)
    .then(position => {
      // 将 BigNumber 转换为字符串显示
      setAvailableAmount(position.liquidity.toString());
    })
    .catch(err => console.error(err));
}, 500);  // 延迟 500ms，避免用户输入时频繁调用
```

**关键要点**：
- 使用 `debounce` 优化用户体验，避免每次输入都调用合约
- 必须将价格区间对齐到有效 Tick（根据费率档位的 spacing）
- `position.liquidity` 返回的是 BigNumber 类型，需要转换为字符串

## 二、计算资金池地址

### 2.1 为什么需要计算资金池地址？

虽然我们有 `getPosition` 辅助函数来获取仓位信息，但在调用 `burn` 和 `collect` 时，我们需要**直接与资金池合约交互**，因此需要知道资金池的合约地址。

### 2.2 CREATE2 地址计算原理

UniswapV3 使用 CREATE2 操作码创建资金池，这意味着：
- 资金池地址是**确定性**的，可以提前计算
- 地址取决于：工厂合约地址 + 盐值（salt）+ 合约字节码哈希

CREATE2 地址计算公式：

$$
\text{address} = \text{keccak256}(0xff \parallel \text{factory} \parallel \text{salt} \parallel \text{bytecodeHash})[12:]
$$

其中：
- `factory` 是工厂合约地址
- `salt` 是盐值（由 tokenA、tokenB、fee 计算得出）
- `bytecodeHash` 是资金池合约的字节码哈希

### 2.3 前端实现 CREATE2 计算

幸运的是，Ethers.js 提供了 `getCreate2Address` 函数，我们可以直接使用：

```javascript
/**
 * 对代币地址进行排序（UniswapV3 要求 token0 < token1）
 */
const sortTokens = (tokenA, tokenB) => {
  return tokenA.toLowerCase() < tokenB.toLowerCase()
    ? [tokenA, tokenB]
    : [tokenB, tokenA];
}

/**
 * 计算资金池的 CREATE2 地址
 * @param factory 工厂合约地址
 * @param tokenA 第一个代币地址
 * @param tokenB 第二个代币地址
 * @param fee 费率档位（500/3000/10000）
 * @returns 资金池合约地址
 */
const computePoolAddress = (factory, tokenA, tokenB, fee) => {
  // 1. 对代币地址排序（确保 token0 < token1）
  [tokenA, tokenB] = sortTokens(tokenA, tokenB);

  // 2. 使用 Ethers.js 的 getCreate2Address 函数计算地址
  return ethers.utils.getCreate2Address(
    factory,  // 工厂合约地址
    // 盐值 = keccak256(abi.encodePacked(token0, token1, fee))
    ethers.utils.keccak256(
      ethers.utils.solidityPack(
        ['address', 'address', 'uint24'],
        [tokenA, tokenB, fee]
      )
    ),
    poolCodeHash  // 资金池合约的字节码哈希（需要预先计算）
  );
}
```

### 2.4 获取资金池合约字节码哈希

## 三、移除流动性的完整流程

### 3.1 移除流动性的两个步骤

移除流动性需要调用两个函数：
1. **burn**：销毁流动性，释放代币（但代币还在池子里）
2. **collect**：实际提取代币到用户账户

### 3.2 前端实现代码

```javascript
/**
 * 移除流动性的完整流程
 * 步骤1: 调用 burn 销毁流动性
 * 步骤2: 从交易回执中获取释放的代币数量
 * 步骤3: 调用 collect 提取代币
 */
const removeLiquidity = (e) => {
  e.preventDefault();

  // 1. 参数验证
  if (!token0 || !token1) {
    console.error("代币未选择");
    return;
  }

  setLoading(true);

  // 2. 计算价格区间对应的 Tick 值（并对齐到有效 Tick）
  const lowerTick = nearestUsableTick(
    priceToTick(lowerPrice),
    feeToSpacing[fee]
  );
  const upperTick = nearestUsableTick(
    priceToTick(upperPrice),
    feeToSpacing[fee]
  );

  // 3. 调用 burn 函数销毁流动性
  pool.burn(lowerTick, upperTick, amount)
    .then(tx => tx.wait())  // 等待交易确认
    .then(receipt => {
      // 4. 从交易回执中提取 Burn 事件
      if (!receipt.events[0] || receipt.events[0].event !== "Burn") {
        throw Error("Missing Burn event after burning!");
      }

      // 5. 获取释放的代币数量
      const amount0Burned = receipt.events[0].args.amount0;
      const amount1Burned = receipt.events[0].args.amount1;

      // 6. 调用 collect 函数提取代币
      return pool.collect(
        account,         // 接收代币的地址（用户账户）
        lowerTick,       // 价格区间下界
        upperTick,       // 价格区间上界
        amount0Burned,   // 要提取的 token0 数量
        amount1Burned    // 要提取的 token1 数量
      );
    })
    .then(tx => tx.wait())  // 等待 collect 交易确认
    .then(() => {
      setLoading(false);
      toggle();  // 关闭对话框或刷新界面
      console.log("流动性移除成功！");
    })
    .catch(err => {
      setLoading(false);
      console.error("移除流动性失败:", err);
    });
}
```

### 3.3 关键步骤解析

#### 步骤 1：调用 burn 销毁流动性

```javascript
pool.burn(lowerTick, upperTick, amount)
```

**功能**：
- 销毁用户指定数量的流动性
- 更新仓位信息，计算应释放的代币数量
- 发出 `Burn` 事件，包含释放的代币数量

**注意**：此时代币还在池子里，没有真正转给用户！

#### 步骤 2：解析 Burn 事件

```javascript
const amount0Burned = receipt.events[0].args.amount0;
const amount1Burned = receipt.events[0].args.amount1;
```

**为什么要从事件中获取数量？**
- `burn` 函数内部会计算实际释放的代币数量
- 由于价格变化和手续费累积，实际数量可能与预期不同
- 从事件中获取**精确的实际值**，避免计算误差

#### 步骤 3：调用 collect 提取代币

```javascript
pool.collect(account, lowerTick, upperTick, amount0Burned, amount1Burned)
```

**功能**：
- 将之前 `burn` 释放的代币转账给用户
- 同时可以提取累积的手续费
- 实际转账操作，代币会发送到 `account` 地址

## 四、最佳实践与注意事项

### 4.1 错误处理

```javascript
// ✅ 推荐：完善的错误处理
try {
  const tx = await pool.burn(lowerTick, upperTick, amount);
  const receipt = await tx.wait();

  // 验证交易是否成功
  if (receipt.status !== 1) {
    throw new Error("交易执行失败");
  }

  // 验证 Burn 事件
  const burnEvent = receipt.events.find(e => e.event === "Burn");
  if (!burnEvent) {
    throw new Error("未找到 Burn 事件");
  }

  // ... 继续执行 collect
} catch (err) {
  // 区分不同类型的错误
  if (err.code === "INSUFFICIENT_FUNDS") {
    alert("Gas 费用不足");
  } else if (err.message.includes("insufficient liquidity")) {
    alert("流动性不足");
  } else {
    alert("操作失败：" + err.message);
  }
}
```

### 4.2 用户体验优化

```javascript
// 1. 显示加载状态
setLoading(true);
setLoadingMessage("正在销毁流动性...");

// 2. 提供进度反馈

    return tx.wait();
  })
  .then(receipt => {
    setLoadingMessage("正在提取代币（2/2）...");
    // ...
  });

// 3. 显示交易哈希，让用户可以查看
console.log("交易哈希:", tx.hash);
```

### 4.3 Gas 优化建议

| 优化点 | 说明 |
|-------|------|
| **批量操作** | 如果要移除多个仓位，考虑使用批量调用 |
| **准确数量** | 从 Burn 事件获取准确数量，避免 collect 时的计算开销 |
| **估算 Gas** | 调用前先估算 Gas，避免失败浪费 Gas |

```javascript
// Gas 估算示例
const gasEstimate = await pool.estimateGas.burn(lowerTick, upperTick, amount);
console.log("预计消耗 Gas:", gasEstimate.toString());
```

### 4.4 安全检查清单

- [ ] **滑点保护**：检查实际获得的代币数量是否符合预期
- [ ] **截止时间**：设置交易截止时间，避免长时间挂起
- [ ] **余额验证**：提取后验证用户余额是否正确增加
- [ ] **事件验证**：确保 Burn 和 Collect 事件都成功发出
- [ ] **重入防护**：避免在回调中再次调用相同函数
