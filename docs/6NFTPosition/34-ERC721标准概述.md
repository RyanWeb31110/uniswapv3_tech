# UniswapV3 技术学习系列（三十四）：ERC721 标准概述

## 系列介绍

在前面的文章中，我们已经实现了 UniswapV3 的核心功能：集中流动性、跨 Tick 交换、手续费累积、价格预言机、闪电贷等。现在，我们将进入一个全新的模块——**NFT 仓位管理**。

这一章是第六个里程碑的开篇，我们将探讨如何将流动性仓位（Liquidity Position）与 NFT（Non-Fungible Token，非同质化代币）结合起来，让每个流动性仓位都成为一个独一无二的 ERC721 代币。

本章将为 NFT 仓位管理打下理论基础，主要内容包括：

1. 理解 ERC721 标准的核心概念
2. 了解 ERC721 与 ERC20 的本质区别
3. 掌握 NFT 元数据的存储方式
4. 理解流动性仓位与 NFT 的相似性
5. 为后续实现 NFT 仓位管理器做准备

让我们开始探索 NFT 在 DeFi 中的应用吧！🎯

## 一、为什么流动性仓位需要 NFT？

在 UniswapV2 中，流动性提供者（LP）获得的是 **ERC20 代币**作为流动性凭证。所有的 LP Token 都是同质化的，因为：

- 所有流动性都分布在整个价格曲线上
- 每个 LP 提供的流动性是完全相同的
- 流动性可以自由拆分和合并

但在 UniswapV3 中，情况完全不同了！由于引入了 **集中流动性**（Concentrated Liquidity），每个流动性仓位都有以下特点：

- ✅ **价格区间不同**：每个 LP 可以选择不同的价格区间（tickLower 和 tickUpper）
- ✅ **流动性数量不同**：即使价格区间相同，流动性数量也可能不同
- ✅ **手续费累积不同**：不同时间、不同价格区间的手续费收益各不相同
- ✅ **无法互换**：两个仓位即使看起来相似，也不能直接互换

这种 **非同质化** 的特性，使得流动性仓位天然适合用 NFT 来表示！每个 NFT 代表一个独特的流动性仓位，包含了该仓位的所有信息。

## 二、ERC721 标准概述

### 2.1 什么是 ERC721？

**ERC721** 是以太坊上定义 NFT 合约的标准，由 [EIP-721](https://eips.ethereum.org/EIPS/eip-721) 提出。它是 ERC20 的一个变体，但引入了"非同质化"的核心概念。

### 2.2 ERC721 与 ERC20 的核心区别

让我们用表格对比一下：

| 特性 | ERC20 | ERC721 |
|------|-------|--------|
| **同质化** | 所有代币完全相同，可互换 | 每个代币都是独一无二的 |
| **标识方式** | 通过数量（amount）标识 | 通过唯一 ID（tokenId）标识 |
| **所有权** | 记录每个地址的总余额 | 记录每个代币 ID 的拥有者 |
| **转账单位** | 任意数量的代币 | 单个代币（通过 tokenId） |
| **应用场景** | 货币、积分、股份 | 收藏品、资产凭证、身份证明 |
| **特有功能** | `transfer(to, amount)` | `transferFrom(from, to, tokenId)` |

### 2.3 ERC721 的核心特性

#### 1. 唯一标识符（Token ID）

每个 ERC721 代币都有一个唯一的 `tokenId`，通常是一个递增的计数器：

```solidity
// ERC721 的核心存储结构
mapping(uint256 => address) private _owners;  // tokenId => owner
mapping(address => uint256) private _balances; // owner => token count
```

#### 2. 所有权跟踪

与 ERC20 不同，ERC721 不仅跟踪地址的代币总数，还跟踪每个代币的具体拥有者：

```solidity
/// @notice 查询代币的拥有者
/// @param tokenId 代币的唯一 ID
/// @return owner 代币拥有者的地址
function ownerOf(uint256 tokenId) public view returns (address owner);

/// @notice 查询地址拥有的代币数量
/// @param owner 地址
/// @return balance 代币数量
function balanceOf(address owner) public view returns (uint256 balance);
```

#### 3. 授权机制

ERC721 提供了两种授权方式：

```solidity
// 方式 1: 授权单个代币
function approve(address to, uint256 tokenId) external;

// 方式 2: 授权所有代币
function setApprovalForAll(address operator, bool approved) external;
```

#### 4. 转账功能

```solidity
// 安全转账（推荐）
function safeTransferFrom(
    address from,
    address to,
    uint256 tokenId
) external;

// 普通转账
function transferFrom(
    address from,
    address to,
    uint256 tokenId
) external;
```

## 三、ERC721 的最大创新：tokenURI 函数

### 3.1 为什么需要 tokenURI？

NFT 的核心价值在于它关联的**资产**（图片、音乐、视频、游戏道具等）。但这些资产通常**不会直接存储在区块链上**，因为：

- 💰 **成本高昂**：在以太坊上存储数据非常昂贵
- 📦 **数据量大**：一张高清图片可能有几 MB，无法直接上链
- 🔄 **不可变性**：上链后难以修改

因此，ERC721 定义了 `tokenURI` 函数，用于**链接链上代币 ID 与链下资产**：

```solidity
/// @notice 返回代币的元数据 URI
/// @param tokenId 代币的唯一 ID
/// @return uri 元数据的链接或内联数据
function tokenURI(uint256 tokenId) external view returns (string memory uri);
```

### 3.2 链下存储方式

`tokenURI` 通常返回一个 **HTTP 链接**，指向一个 JSON 文件：

```solidity
function tokenURI(uint256 tokenId) public view returns (string memory) {
    return string(abi.encodePacked(
        "https://api.example.com/metadata/",
        Strings.toString(tokenId),
        ".json"
    ));
}
```

返回的 JSON 文件格式如下（来自 [OpenZeppelin 文档](https://docs.openzeppelin.com/contracts/4.x/erc721)）：

```json
{
    "name": "Thor's hammer",
    "description": "Mjölnir, the legendary hammer of the Norse god of thunder.",
    "image": "https://game.example/item-id-8u5h2m.png",
    "strength": 20
}
```

**字段说明**：
- `name`：代币的名称
- `description`：代币或集合的描述
- `image`：代币图像的 HTTP 链接
- 自定义属性：如 `strength`，可以是任意 JSON 字段

### 3.3 链上存储方式（Data URI）

虽然成本高昂，但我们也可以将元数据和图像**完全存储在链上**。这种方式的优势是：

- ✅ **完全去中心化**：不依赖任何外部服务器
- ✅ **永久存在**：只要以太坊存在，数据就永久可访问
- ✅ **无需信任**：不必担心外部链接失效

**实现方式**：使用 **Data URI Scheme**，将数据直接编码到 URI 中：

```solidity
function tokenURI(uint256 tokenId) public view returns (string memory) {
    string memory json = string(abi.encodePacked(
        '{',
            '"name": "Uniswap V3 Position #', Strings.toString(tokenId), '",',
            '"description": "This NFT represents a liquidity position in a Uniswap V3 pool.",',
            '"image": "data:image/svg+xml;base64,', _generateSVG(tokenId), '"',
        '}'
    ));

    return string(abi.encodePacked(
        'data:application/json;base64,',
        Base64.encode(bytes(json))
    ));
}
```

**Data URI 格式**：
```
data:[<mediatype>][;base64],<data>
```

示例：
- JSON 数据：`data:application/json;base64,eyJuYW1lIjoi...`
- SVG 图像：`data:image/svg+xml;base64,PHN2ZyB3aWR0aD0i...`

### 3.4 为什么使用 SVG？

链上存储图像时，我们通常使用 **SVG（可缩放矢量图形）**格式，原因是：

1. **文本格式**：SVG 是基于 XML 的文本格式，易于在 Solidity 中生成
2. **体积小**：相比位图（PNG、JPG），SVG 文件更小
3. **动态生成**：可以根据代币属性动态生成图像
4. **无限缩放**：矢量图可以无损缩放

**SVG 模板示例**：

```solidity
function _generateSVG(uint256 tokenId) internal pure returns (string memory) {
    return Base64.encode(bytes(string(abi.encodePacked(
        '<svg xmlns="http://www.w3.org/2000/svg" width="290" height="500">',
            '<rect width="290" height="500" fill="#2c3e50"/>',
            '<text x="145" y="250" text-anchor="middle" fill="white" font-size="24">',
                'Position #', Strings.toString(tokenId),
            '</text>',
        '</svg>'
    ))));
}
```

## 四、流动性仓位与 NFT 的完美结合

### 4.1 为什么它们如此相似？

让我们对比一下流动性仓位和 NFT 的特性：

| 特性 | UniswapV3 流动性仓位 | ERC721 NFT |
|------|---------------------|------------|
| **唯一性** | 每个仓位由 (owner, tickLower, tickUpper) 唯一标识 | 每个 NFT 由 tokenId 唯一标识 |
| **非同质化** | 不同仓位不可互换 | 不同 NFT 不可互换 |
| **所有权** | 记录每个仓位的拥有者 | 记录每个 tokenId 的拥有者 |
| **可转让** | 仓位可以转移给其他地址 | NFT 可以转移给其他地址 |
| **可视化** | 仓位信息（价格区间、流动性等） | NFT 元数据（图像、属性等） |

### 4.2 融合的优势

将流动性仓位封装为 NFT，可以获得以下优势：

1. **🎨 可视化展示**：每个仓位可以生成独特的 SVG 图像，直观展示价格区间和流动性
2. **💼 资产管理**：可以在 OpenSea 等 NFT 市场查看和管理仓位
3. **🔄 可交易性**：仓位可以作为 NFT 在二级市场交易
4. **🧩 可组合性**：可以与其他 DeFi 协议组合（如借贷抵押）
5. **📊 链上元数据**：价格区间、流动性、手续费等信息都可以编码到链上

### 4.3 实现思路

在 UniswapV3 中，我们将创建一个 **NonfungiblePositionManager** 合约，它：

1. ✅ 继承 ERC721 标准
2. ✅ 为每个流动性仓位分配唯一的 tokenId
3. ✅ 实现 `tokenURI` 函数，生成链上 SVG 和 JSON 元数据
4. ✅ 提供 `mint`、`burn`、`increaseLiquidity`、`decreaseLiquidity` 等管理函数
5. ✅ 处理多池子、多仓位的复杂场景

**核心数据结构设计**：

```solidity
contract NonfungiblePositionManager is ERC721 {
    // 仓位信息结构体
    struct Position {
        address pool;       // 所属池子
        int24 tickLower;    // 价格区间下限
        int24 tickUpper;    // 价格区间上限
        uint128 liquidity;  // 流动性数量
        uint256 feeGrowthInside0LastX128;  // 手续费累积快照
        uint256 feeGrowthInside1LastX128;
        uint128 tokensOwed0;  // 待领取的手续费
        uint128 tokensOwed1;
    }

    // tokenId => Position
    mapping(uint256 => Position) public positions;

    uint256 private _nextId = 1;  // tokenId 计数器

    /// @notice 铸造新的仓位 NFT
    function mint(MintParams calldata params) external returns (uint256 tokenId) {
        tokenId = _nextId++;
        _mint(msg.sender, tokenId);

        positions[tokenId] = Position({
            pool: params.pool,
            tickLower: params.tickLower,
            tickUpper: params.tickUpper,
            liquidity: params.liquidity,
            // ...
        });
    }
}
```

## 五、知识点回顾

本章我们学习了 ERC721 标准的核心概念，为后续实现 NFT 仓位管理打下了基础。让我们回顾一下关键知识点：

### 5.1 核心概念

1. **ERC721 是什么？**
   - 以太坊上定义 NFT 的标准
   - 每个代币都有唯一的 tokenId
   - 不可互换，适合表示独特资产

2. **ERC721 vs ERC20**
   - ERC20：同质化，按数量转账
   - ERC721：非同质化，按 tokenId 转账

3. **tokenURI 函数**
   - 链接代币 ID 与元数据
   - 可以返回 HTTP 链接（链下存储）
   - 也可以返回 Data URI（链上存储）

4. **链上存储方案**
   - 使用 SVG 格式生成图像
   - 使用 Base64 编码嵌入 Data URI
   - 成本高但完全去中心化

### 5.2 流动性仓位的 NFT 化

1. **为什么需要 NFT？**
   - UniswapV3 的仓位是非同质化的
   - 每个仓位有不同的价格区间和流动性
   - NFT 天然适合表示这种独特性

2. **NFT 化的优势**
   - 可视化展示
   - 资产管理便利
   - 可组合性强
   - 链上元数据
